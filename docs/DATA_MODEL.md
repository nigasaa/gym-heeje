# 데이터와 업데이트 유지 규칙

DB 이름은 `gym-heeje`, 현재 형식 버전은 1입니다. 배포할 때마다 DB 이름을 바꾸거나 삭제하지 않습니다.

| 저장 영역 | 데이터 |
|---|---|
| categories | id, name, sortOrder |
| exercises | id, name, categoryId, sortOrder, source, editVersion, createdAt, updatedAt |
| snapshots | id, exerciseId, revision, savedAt, unit, sets |
| meta | seedVersion, formatHelpDismissed, persistenceRequested, deletedBuiltin:<운동 ID> |

각 set은 `id`, `weight`, `reps`만 가집니다. 번호는 배열 위치 + 1, 개수는 배열 길이입니다. `unit`은 저장본에 한 번만 존재하며 `setCount`, 대표 중량, 현재 세트 복사본은 저장하지 않습니다.

현재 설정 = 해당 운동에서 revision이 가장 큰 저장본. 이전 설정 = 그다음 최대 5개. `[exerciseId, revision]` 유일 인덱스를 역순으로 읽고 최대 6개에서 조회를 멈춥니다. 오래된 기록을 자동 삭제하지 않습니다.

저장 시 unit·세트 길이·순서·중량·반복을 비교합니다. ID와 숫자 표시 문자열 차이는 변경이 아닙니다. A→B→A를 각각 저장하면 3건입니다.

읽은 저장본은 숫자 범위, 세트 ID 중복, 단위, 날짜·순번을 확인합니다. 손상된 운동은 편집을 차단하고 나머지는 조회할 수 있습니다. 기존 DB를 지워서 오류를 숨기지 않습니다.

## 하나로 묶이는 저장 작업

설정 저장은 다음을 하나의 읽기/쓰기 트랜잭션에서 처리합니다.

1. 운동 존재와 편집 시작 시의 editVersion 확인
2. 최신 저장본 조회 및 최종 입력과 비교
3. revision + 1로 전체 저장본 생성
4. 운동 editVersion + 1과 수정 시각 갱신
5. 트랜잭션 전체 성공 후 UI에 성공 표시

생성은 이름 중복 검사·정렬 순서 계산·운동 생성·첫 저장본 생성을 함께 처리합니다. 삭제는 운동과 그 운동의 모든 저장본을 함께 삭제합니다. 실패하면 전부 롤백합니다. 다른 운동의 데이터는 건드리지 않습니다.

v1.1부터 기본 운동도 명시적인 확인 후 삭제할 수 있습니다. 기본 운동 삭제는 `meta`에 `deletedBuiltin:<운동 ID> = true`를 쓰는 작업까지 같은 트랜잭션에 묶습니다. 재실행 시 삭제 표시가 있는 기본 운동의 부재를 정상으로 판단하며 재생성하지 않습니다. 표시 없이 기본 데이터가 누락되었다면 오류를 알리고 데이터를 초기화하지 않습니다. 기본 운동을 전부 삭제한 상태도 정상입니다.

이번 변경은 기존 meta 저장소의 허용된 boolean 값을 사용하므로 DB 버전은 1을 유지합니다. 앱 버전 1.1.0과 DB 버전 1은 서로 다른 개념입니다. 초기 v1 명세서의 기본 운동 삭제 금지 조건은 사용자 후속 요청으로 변경되었습니다.

## 앱 화면 업데이트

서비스 워커는 앱 파일만 캐시합니다. 앱 데이터는 IndexedDB에 별도로 남습니다. Workbox의 앱 전용 캐시 이름을 사용하고, 넓은 범위의 과거 캐시 삭제 기능은 사용하지 않습니다. 같은 앱 캐시 안의 더 이상 필요한 파일이 아닌 항목은 Workbox의 기본 precache 활성화 절차로 정리합니다.

새 버전은 먼저 대기합니다. 메인에서 사용자가 업데이트를 선택한 창만 새로고침합니다. 다른 창에서 열려 있는 편집본은 자동 새로고침하지 않습니다. 처음 기본 운동을 등록하는 seed 절차 역시 첫 초기화에만 실행합니다.

## 미래 형식 변경 시 개발 규칙

현재 버전에는 형식 변경이 아직 없으므로 v1→v2 변환 코드를 가짜로 넣지 않았습니다. 추후 필드가 바뀌면 DB 버전과 명시적인 이전 절차를 함께 추가해야 합니다. 그때도 앱 업데이트를 이유로 DB를 삭제하거나 새 이름의 빈 DB로 바꾸지 않습니다.

- `upgrade` 트랜잭션 안에서 기존 데이터를 새로운 형식으로 이전합니다.
- 강제로 실패시킨 이전 테스트에서 원래 데이터와 DB 버전이 유지되는지 확인합니다.
- 구버전 코드가 새 DB 형식에 쓰기를 시도하지 않도록 차단합니다.
- 다른 창이 이전을 막으면 연결을 닫고 안내하며, 데이터 삭제로 해결하지 않습니다.
- 실제 사용자 데이터를 테스트 자료로 사용하지 않습니다.

`tests/fixtures/v1.0-app`에는 실제 이전 앱 빌드만 보관합니다. 테스트가 그 앱의 빈 임시 저장 공간에 예시 기록을 입력한 뒤 현재 배포 빌드로 업데이트합니다. 기본 운동, 사용자 추가 운동, 소수 중량, 단위, 과거 이력의 모든 저장 필드를 전후 비교합니다. 사용자가 삭제한 기본 운동이 다음 업데이트에서도 다시 생성되지 않는지도 확인합니다.

동기화를 추가할 때는 현재 revision·editVersion만으로 기기간 충돌을 해결할 수 없습니다. 기기별 변경 ID, 삭제 전파, 충돌 규칙을 별도로 설계해야 합니다.
